## コンテキストが膨らむ理由

Anthropic の Messages API はステートレスです。Working with the Messages API には次のように書かれています。

> The Messages API is stateless, which means that you always send the full conversational history to the API.

<ExLinkCard url="https://platform.claude.com/docs/en/build-with-claude/working-with-messages" />

Agent Loop では、ターンを重ねるたびに Model の応答と Tool の結果が会話に積み上がり、それをすべて送り直します。
1 ターン目に読んだファイルの内容は、最終出力を返すまで毎ターン入力トークンとして数えられます。
そのため、入力トークンの合計はターン数に比例するのではなく、ターンを重ねるほど急に増えていきます。

コンテキストが長くなると、料金だけでなく回答の質にも影響します。Anthropic の「Effective context engineering for AI agents」では、コンテキストが長くなるほど Model が情報を正確に思い出せなくなる現象を context rot と呼んでいます。

> as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases.

同じ記事によると、LLM には「attention budget」があり、トークンが 1 つ増えるたびにその予算を消費します。

> LLMs have an "attention budget" that they draw on when parsing large volumes of context. Every new token introduced depletes this budget by some amount

<ExLinkCard url="https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents" />

Agent に送るコンテキストは、大きく分けて Tool の定義、Instructions、会話 (ユーザーの入力、Model の応答、Tool の結果) の 3 つです。
何がコンテキストを膨らませているかによって、選ぶ対策は異なります。この記事で扱う対策は次のとおりです。

| 膨らませているもの | 対策 | この記事での扱い |
| --- | --- | --- |
| 毎ターン送り直す会話 | プロンプトキャッシュ | 計測 |
| 大きな Tool の結果 | Tool の結果のクリア | 計測 |
| 長く続く会話そのもの | 会話の圧縮 | 計測 |
| 消した後に必要になる情報 | メモリ | 計測 |
| 多数の Tool の定義 | Tool Search | 計測 |
| 多数の Tool の定義、大きな Tool の結果 | Code Execution | 紹介のみ |
| 調査の途中経過 | サブ Agent | 紹介のみ |

以降のセクションでは、表の上から順に対策を適用し、結果を比べます。

## リポジトリ調査 Agent

題材にはリポジトリのソースコードを読んで質問に答える Agent を使います。
ファイルの内容を読むたびに大きな Tool の結果が会話に積み上がるため、コンテキストが膨らみやすい題材です。

調査対象は 1 本目の記事でも扱った OpenAI Agents SDK の v0.23.1 です。

<ExLinkCard url="https://github.com/openai/openai-agents-python" />

Agent には、ディレクトリを一覧する `list_files`、正規表現で検索する `grep`、ファイルを読む `read_file` の 3 つの Tool を持たせます。
`read_file` はファイルの内容をすべて返す素朴な実装にしています。

```go
{
	Name:        "read_file",
	Description: "リポジトリ内のファイルの内容をすべて返します。",
	Properties: map[string]any{
		"path": map[string]any{"type": "string", "description": "リポジトリのルートからの相対パス"},
	},
	Required: []string{"path"},
	Run: func(_ context.Context, input json.RawMessage) (string, error) {
		var in struct{ Path string }
		if err := json.Unmarshal(input, &in); err != nil {
			return "", err
		}
		b, err := fs.ReadFile(repo, path.Clean(in.Path))
		if err != nil {
			return "", err
		}
		return string(b), nil
	},
},
```

Agent に与える質問は、SDK の各所に散らばった既定値や名前を問う 10 問です。

```go
const prompt = `src/agents のソースコードを読んで、次の質問に答えてください。

q1. Runner.run の max_turns の既定値
q2. max_turns を超えたときに送出される例外のクラス名
q3. MCPServerStdio の client_session_timeout_seconds の既定値
q4. function_tool デコレーターの timeout_behavior の既定値
q5. RunConfig の workflow_name の既定値
q6. RunConfig の tool_not_found_behavior の既定値
q7. Tool の実行に失敗したときに、既定で Model に返されるメッセージの文字列
q8. name が "Billing Agent" の Agent へ Handoff するときの、既定の Tool の名前
q9. 入力のガードレールの tripwire が発火したときに送出される例外のクラス名
q10. Agent の tool_use_behavior の既定値

最後に、q1 から q10 をキーとし、答えを値とした JSON オブジェクトを ` + "```json" + ` のコードブロックで出力してください。数値は数値型、それ以外は文字列型にしてください。`
```

最終出力の JSON を正解と比べ、正解数を数えます。正解はすべて v0.23.1 のソースコードで確認しています。

- ソースコード: [GitHub](https://github.com/p1ass/blog/tree/main/app/routes/posts/agent-context-management/repo-agent)

### 計測する指標

2 本目の記事と同様に、Agent Loop の中でターン数、Tool Call とエラーの回数、トークンを集計します。
この記事では入力トークンをキャッシュの読み込みと書き込みに分け、1 回のリクエストで送ったコンテキストの最大長 (`PeakContext`) も記録します。

```go
func (u *Usage) add(turn int, resp *anthropic.BetaMessage) {
	ru := resp.Usage
	u.InputTokens += ru.InputTokens
	u.CacheWriteTokens += ru.CacheCreationInputTokens
	u.CacheReadTokens += ru.CacheReadInputTokens
	u.OutputTokens += ru.OutputTokens
	u.PeakContext = max(u.PeakContext, ru.InputTokens+ru.CacheCreationInputTokens+ru.CacheReadInputTokens)
	// ...
}
```

Anthropic の API が返す `input_tokens` にはキャッシュから読み込んだ分と、キャッシュに書き込んだ分が含まれません。
3 つを足したものが、そのリクエストで送った入力トークンの合計です。

料金は Claude Sonnet 5.5 の入力の単価 ($2 / 100 万トークン) に、キャッシュの書き込みは 1.25 倍、読み込みは 0.1 倍の倍率を掛けて計算します。
この記事で扱う対策はどれも入力トークンを減らすものなので、出力トークンの料金は含めていません。

## プロンプトキャッシュ

プロンプトキャッシュは、リクエストの先頭から一致する部分をキャッシュから読み込む機能です。
Agent Loop では前のターンまでの会話がそのまま先頭に残るため、送り直す部分の大半をキャッシュから読めます。

キャッシュは `tools`、`system`、`messages` の順に先頭から作られ、途中が変わるとそこから後ろはキャッシュから読めなくなります。

> Cache prefixes are created in the following order: `tools`, `system`, then `messages`. This order forms a hierarchy where each level builds upon the previous ones.

<ExLinkCard url="https://platform.claude.com/docs/en/build-with-claude/prompt-caching" />

リクエストのトップレベルに `cache_control` を付けると、最後のキャッシュ可能なブロックにキャッシュの区切りが置かれます。
会話が伸びると区切りも後ろへ動くので、Agent Loop と相性がよい指定方法です。

> With automatic caching, the cache point moves forward automatically as conversations grow.

Go では、`CacheControl` を指定します。

```go
if c.Cache {
	p.CacheControl = anthropic.NewBetaCacheControlEphemeralParam()
}
```

キャッシュの有効期間は、何も指定しなければ 5 分、`ttl: "1h"` を指定すると 1 時間です。キャッシュを読むたびに期間が延びます。
料金は通常の入力に比べて、キャッシュの書き込みが 1.25 倍 (1 時間の場合は 2 倍)、読み込みが 0.1 倍です。読み込みの倍率は Claude Fable 5.1 では 0.025 倍、Claude Opus 5.5 では 0.05 倍と、モデルによって異なります。

キャッシュできる先頭部分には最小の長さがあり、Claude Sonnet 5.5 では 512 トークンです。
これより短いとキャッシュされませんが、エラーにはならずそのまま処理されます。

### キャッシュの実行結果

```text
$ go run . -repo ../openai-agents-python -n 1 -cache
run 1: turns=5 calls=9 errors=0 input_tokens=171011 cache_read=115048 cache_write=55951 output_tokens=1711 peak_context=55953 clears=0 compactions=0 compaction_tokens=0 score=10/10
```

入力トークンの合計 171,011 のうち、115,048 をキャッシュから読み込み、55,951 をキャッシュに書き込みました。料金は約 $0.16 で、ベースラインの半分以下です。

入力トークンの合計はほとんど変わらず、料金だけが下がっています。
キャッシュはコンテキストの長さを変えないので、context rot への対策にはなりません。

また、書き込みが 1.25 倍の料金になるため、ターン数が少ないと書き込みの割合が大きくなります。
この実行では料金の 8 割以上が書き込みの分でした。

### キャッシュが外れる操作

Tool の定義 (名前、説明、引数) を変えると、キャッシュ全体が無効になります。

> Modifying tool definitions (names, descriptions, parameters) invalidates the entire cache

会話の途中で Tool の定義を差し替えたり、`system` を書き換えたりすると、そのリクエストではキャッシュをほとんど読めません。
Agent Loop の途中で変えたい指示があれば、`system` を書き換えずに会話へ足すほうがキャッシュを保てます。

## 圧縮とクリアのタイミング

プロンプトキャッシュは料金を下げますが、コンテキストの長さは変えません。
コンテキストそのものを短くするには、古い Tool の結果をクリアするか、会話を要約して圧縮します。

Effective context engineering for AI agents は、Tool の結果のクリアを最も安全で手軽な圧縮の 1 つとしています。

> One of the safest lightest touch forms of compaction is tool result clearing, most recently launched as a feature on the Claude Developer Platform.

Anthropic の API では、どちらもサーバー側の機能として提供されています。
いつ発動させるかは、入力トークンの閾値で指定します。

### 古い Tool の結果のクリア

`context_management` に `clear_tool_uses_20250919` を指定すると、入力トークンが `trigger` を超えたときに、古い Tool の結果から順にプレースホルダーへ置き換えます。
直近の Tool の結果は、`keep` で指定した数 (指定しなければ 3 つ) だけ残ります。

<ExLinkCard url="https://platform.claude.com/docs/en/build-with-claude/context-editing" />

Tool の結果を消すと、そこから後ろはキャッシュから読めなくなります。
そのため、1 回に消すトークン数の下限を `clear_at_least` で指定し、少しずつ消してキャッシュを何度も作り直すことを避けます。

> Invalidates cached prompt prefixes when content is cleared. To account for this, clear enough tokens to make the cache invalidation worthwhile. Use the `clear_at_least` parameter to ensure a minimum number of tokens is cleared each time.

Go SDK では Beta の API から指定します。

```go
if c.ClearTrigger > 0 {
	p.Betas = append(p.Betas, anthropic.AnthropicBetaContextManagement2025_06_27)
	p.ContextManagement.Edits = append(p.ContextManagement.Edits, anthropic.BetaContextManagementConfigEditUnionParam{
		OfClearToolUses20250919: &anthropic.BetaClearToolUses20250919EditParam{
			Trigger:      anthropic.BetaClearToolUses20250919EditTriggerUnionParam{OfInputTokens: &anthropic.BetaInputTokensTriggerParam{Value: c.ClearTrigger}},
			ClearAtLeast: anthropic.BetaInputTokensClearAtLeastParam{Value: c.ClearAtLeast},
		},
	})
}
```

ベースラインの最大長が約 72,000 トークンだったので、40,000 トークンを超えたらクリアし、1 回に 20,000 トークン以上を消す設定で実行しました。

$ go run . -repo ../openai-agents-python -n 1 -cache -clear 40000 -clear-at-least 20000

最大長は 28,856 トークンに収まり、料金は約 $0.09 でした。10 問すべてに正解しています。

### 会話の圧縮

会話の圧縮 (compaction) は、それまでの会話を要約して置き換える機能です。
Effective context engineering for AI agents では次のように説明しています。

> Compaction is the practice of taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary.

Anthropic の API には、2 つの方式があります。

- 閾値方式 (`compact_20260112`) では、`context_management` に指定した `trigger` を入力トークンが超えたときにサーバーが要約します。`trigger` を指定しなければ 150,000 トークンで、最小は 50,000 トークンです
- オンデマンド方式は、トップレベルに `"compaction": {"type": "summarize"}` を指定したリクエストで要約を作ります。要約された元のメッセージは、クライアントが会話から取り除きます

<ExLinkCard url="https://platform.claude.com/docs/en/build-with-claude/compaction" />

ドキュメントは、使える環境ではオンデマンド方式を推奨しています。

> Use on-demand compaction wherever it is available.

ただし、オンデマンド方式は `context_management` と同じリクエストでは使えません。

> You can't combine `compaction` with `context_management` on one request.

この記事では Tool の結果のクリアと組み合わせて比べたいので、クリアと同じく `context_management` に指定できる閾値方式を使います。
クリアを使わない場合は、オンデマンド方式を検討するのがよいでしょう。

```go
if c.CompactTrigger > 0 {
	p.Betas = append(p.Betas, anthropic.AnthropicBetaCompact2026_01_12)
	p.ContextManagement.Edits = append(p.ContextManagement.Edits, anthropic.BetaContextManagementConfigEditUnionParam{
		OfCompact20260112: &anthropic.BetaCompact20260112EditParam{
			Trigger: anthropic.BetaInputTokensTriggerParam{Value: c.CompactTrigger},
		},
	})
}
```

圧縮の要約を作るためのトークンは、レスポンスの `usage` のトップレベルには含まれず、`iterations` に `compaction` として記録されます。
料金を集計するときは、こちらも足す必要があります。

```go
for _, it := range ru.Iterations {
	if c, ok := it.AsAny().(anthropic.BetaCompactionIterationUsage); ok {
		u.Compactions++
		u.CompactionTokens += c.InputTokens + c.CacheCreationInputTokens + c.CacheReadInputTokens + c.OutputTokens
	}
}
```

### 閾値の決め方

圧縮は会話全体を要約するので、細かい情報が失われます。また、要約を作るたびに Model を呼ぶ料金もかかります。
クリアは古い Tool の結果を消すだけなので、Model の判断の経緯は会話に残ります。

どちらの方法でも、消した情報は取り戻せません。Anthropic の「Scaling Managed Agents」は、次のように指摘しています。

> But irreversible decisions to selectively retain or discard context can lead to failures. It is difficult to know which tokens the future turns will need.

<ExLinkCard url="https://www.anthropic.com/engineering/managed-agents" />

また、圧縮の要約を作るのは、コンテキストが最も長くなった時点の Model です。Claude Code のセッション管理を解説した記事では、context rot のため、圧縮するときの Model は最も賢くない状態にあると説明しています。

> due to context rot, the model is at its least intelligent point when compacting.

<ExLinkCard url="https://claude.com/blog/using-claude-code-session-management-and-1m-context" />

このため、コンテキストウィンドウの上限ぎりぎりまで待たず、余裕のあるうちに発動させるほうが安全です。
以上を踏まえて、閾値は次の順に設定するのがよいと考えています。

1. ベースラインで最大長を計測し、Agent のコンテキストがどこまで伸びるかを確かめる
2. 最大長より低い位置に、Tool の結果のクリアの閾値を置く。`clear_at_least` はキャッシュの書き込みを何度も繰り返さない程度に大きくする
3. クリアしても伸び続ける長い作業に備えて、それより高い位置に圧縮の閾値を置く

今回の質問は 5 ターン前後で終わるため、最大長は 5〜7 万トークンでした。
圧縮の最小値の 50,000 トークンとほぼ同じなので、この規模の作業ではクリアで十分です。

なお、Claude Fable 5.1、Claude Opus 5.5、Claude Sonnet 5.5 では、クライアント側で過去の会話を編集すると、それより後ろの thinking ブロックが無効になります。
サーバー側のクリアや圧縮はこの影響を受けないため、会話を短くしたいときはクライアント側で編集するよりも API の機能を使うほうが安全です。

> On Claude Fable 5.1, Claude Opus 5.5, and Claude Sonnet 5.5, server-side context management never invalidates thinking blocks. Client-side edits to earlier turns can invalidate the thinking blocks in every later assistant turn.

## 消す前にメモリへ書き出す

クリアや圧縮で消えた情報が後で必要になると、Agent はファイルを読み直します。
Effective context engineering for AI agents では、Agent がコンテキストの外にメモを書き残し、後で読み戻す手法を structured note-taking と呼んでいます。

> Structured note-taking, or agentic memory, is a technique where the agent regularly writes notes persisted to memory outside of the context window. These notes get pulled back into the context window at later times.

Anthropic の API には、この手法のための Memory tool があります。

<ExLinkCard url="https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool" />

### Memory tool の仕組み

Memory tool は、クライアント側で実行する Tool です。
Model は `/memories` ディレクトリに対して `view`、`create`、`str_replace`、`insert`、`delete`、`rename` の 6 つのコマンドを呼び、アプリケーションがそれを実際のストレージに対して実行します。

Tool の定義は `{"type": "memory_20250818", "name": "memory"}` の指定だけで済みます。
Memory tool を `tools` に含めると、API が次の指示をシステムプロンプトに自動で追加します。

```text
IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE.
MEMORY PROTOCOL:
1. Use the `view` command of your `memory` tool to check for earlier progress.
2. ... (work on the task) ...
   - As you make progress, record status / progress / thoughts etc in your memory.
ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory.
```

また、Tool の結果のクリアと組み合わせると、コンテキストがクリアの閾値へ近づくと、Model に警告が届きます。

> When your conversation context approaches the configured clearing threshold, Claude receives an automatic warning to preserve important information.

警告がどの時点で、どのような形式で届くかは、ドキュメントに書かれていません。

### Memory tool の実装

Go の SDK には Memory tool のヘルパーがないため、6 つのコマンドを自前で実装しました。

Model が渡すパスは信頼できません。`/memories/../../secrets.env` のようなパスでディレクトリの外へ出る操作を防ぎます。
この実装では、Go の `os.Root` でメモリのディレクトリを開き、その外にあるファイルを操作できないようにしています。

```go
type Memory struct {
	root *os.Root
}

func NewMemory(dir string) (*Memory, error) {
	root, err := os.OpenRoot(dir)
	if err != nil {
		return nil, err
	}
	return &Memory{root: root}, nil
}

func (m *Memory) rel(p string) (string, error) {
	if p != memoryDir && !strings.HasPrefix(p, memoryDir+"/") {
		return "", fmt.Errorf("Error: The path %s must start with %s", p, memoryDir)
	}
	rel := strings.TrimPrefix(strings.TrimPrefix(p, memoryDir), "/")
	if rel == "" {
		return ".", nil
	}
	return rel, nil
}
```

Model からの入力は、Go SDK の `BetaMemoryTool20250818CommandUnion` でデコードし、コマンドごとに処理を分けます。

```go
func (m *Memory) Run(cmd anthropic.BetaMemoryTool20250818CommandUnion) (string, error) {
	switch c := cmd.AsAny().(type) {
	case anthropic.BetaMemoryTool20250818ViewCommand:
		return m.view(c.Path)
	case anthropic.BetaMemoryTool20250818CreateCommand:
		return m.create(c.Path, c.FileText)
	case anthropic.BetaMemoryTool20250818StrReplaceCommand:
		return m.strReplace(c.Path, c.OldStr, c.NewStr)
	case anthropic.BetaMemoryTool20250818InsertCommand:
		return m.insert(c.Path, int(c.InsertLine), c.InsertText)
	case anthropic.BetaMemoryTool20250818DeleteCommand:
		return m.delete(c.Path)
	case anthropic.BetaMemoryTool20250818RenameCommand:
		return m.rename(c.OldPath, c.NewPath)
	}
	return "", fmt.Errorf("Error: unknown command %q", cmd.Command)
}
```

各コマンドの返す文字列は、ドキュメントで推奨されている文言に合わせています。

### Tool Search

Anthropic の Tool Search を使うと、Tool の定義を必要になるまで読み込まないようにできます。
Tool に `defer_loading: true` を付け、`tools` に Tool Search の Tool を加えます。

<ExLinkCard url="https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool" />

```go
if a.ToolSearch {
	tools = append(tools, anthropic.BetaToolUnionParam{OfToolSearchToolRegex20251119: &anthropic.BetaToolSearchToolRegex20251119Param{
		Type: anthropic.BetaToolSearchToolRegex20251119TypeToolSearchToolRegex20251119,
	}})
}
```

```go
if t.Deferred {
	p.DeferLoading = anthropic.Bool(true)
}
```

`defer_loading: true` を付けた Tool は、リクエストの `tools` に含めて送りますが、先頭のプロンプトからは除かれます。
Model が Tool Search で見つけた Tool だけが、会話の中に定義として追加されます。
先頭が変わらないので、プロンプトキャッシュも保たれます。

> The prefix is untouched, so prompt caching is preserved.

Anthropic のコスト削減の記事でも、めったに使わない Tool は `defer_loading` にして、キャッシュする先頭部分から外すよう勧めています。

> Defer rarely used tools. Declare all your tools up front but mark the rarely used ones defer_loading: they stay out of the cached prefix and are appended into the conversation only when Claude looks them up with tool search, so the cache is preserved.

<ExLinkCard url="https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform" />

Tool Search のほかにも、キャッシュを保ったまま会話の途中で Tool を増減する機能が beta で追加されています。
2026 年 7 月には `tools` を書き換えずに Tool を追加・削除できる mid-conversation tool changes が、9 月には会話の途中の system メッセージの中で Tool を定義できる inline tools が加わりました。

上の表のとおり、遅延読み込みにすると 40 個の定義の分がなくなり、Tool Search の Tool の分の 385 トークンが増えるだけになりました。

Effective context engineering for AI agents でも、圧縮や structured note-taking と並ぶ手法として紹介されています。

> specialized sub-agents can handle focused tasks with clean context windows. ... returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens).

ただし、サブ Agent はそれぞれが自分のコンテキストで調査するため、全体のトークンは増えます。Anthropic の Multi-Agent の記事では、同じ作業で 3〜10 倍のトークンを使うと報告しています。

> In our testing, multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks.

## OpenAI の対応する機能

ここまで Anthropic の API を使ってきましたが、OpenAI の Responses API にも対応する機能があります。

プロンプトキャッシュは、何も指定しなくても有効です。GPT-5.6 以降では、キャッシュの有効期間が 30 分、書き込みは 1.25 倍、読み込みは多くのモデルで 0.1 倍です。

<ExLinkCard url="https://developers.openai.com/api/docs/guides/prompt-caching" />

Responses API は `previous_response_id` を指定すると、会話をサーバー側で引き継げます。
ただし、会話を送り直さなくてよくなるだけで、過去の入力も毎回課金されます。

> Even when using `previous_response_id`, all previous input tokens for responses in the chain are billed as input tokens in the API.

<ExLinkCard url="https://developers.openai.com/api/docs/guides/conversation-state" />

会話の圧縮には、`context_management` に `compact_threshold` を指定するサーバー側の圧縮と、`/responses/compact` のエンドポイントがあります。
圧縮の結果は、暗号化された compaction アイテムとして返ります。

<ExLinkCard url="https://developers.openai.com/api/docs/guides/compaction" />

一方で、Tool の結果だけをクリアする機能は見当たりませんでした。
`truncation: "auto"` を指定すると、コンテキストウィンドウを超えたときに会話の先頭から削られますが、古い Tool の結果を選んで消す機能ではありません。

## おわりに

この記事では、リポジトリ調査 Agent を題材に、プロンプトキャッシュ、Tool の結果のクリア、会話の圧縮、メモリ、Tool Search を比べました。

プロンプトキャッシュで入力の料金は $0.37 から $0.16 に下がり、Tool の結果のクリアを加えると、コンテキストの最大長は約 72,000 から約 29,000 トークンに減りました。
一方で、圧縮の閾値に届かない短い作業や、メモリの読み書きでターンが増える作業もあり、ログで Agent の動きを確かめながら閾値を決める必要があります。

次回の記事では、Agent Loop を回す場所であるハーネスについてまとめようと思います。
