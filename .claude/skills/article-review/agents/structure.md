# 構成・論理展開のレビュー

記事全体を通して読み、**読者が最後まで理解しながら読めるか**を検証する。個々の文の正しさより、話の運びを見る。

## 見るもの

### 導入

- 読者が「なぜこの記事を読むのか」を、最初の数段落で理解できるか
- 何をした記事なのかが `{/* <!--more--> */}` より前で分かるか (この位置より前が記事一覧の要約になる)
- 前提知識や制約 (対象バージョン、環境、実験的な機能) を、読者が手順へ進む前に示しているか

### 見出し構成

- 見出しだけを拾い読みして、記事の骨格が分かるか
- 見出しが読者の疑問や作業に沿っているか。実装内部の分類より読者の視点を優先しているか
- 見出しが名詞句か短い文ひとつで完結しているか。ダッシュでサブタイトルを足していないか
- `##` の粒度がそろっているか。極端に長い節や短い節が混ざっていないか
- 1 つの節が 1 つのことを説明しているか。2 つ以上あれば `###` で割る
- 締めが `## おわりに` になっているか

### 論の流れ

- 背景 → 課題 → 手段 → 結果、の順序が自然か
- **判断の理由が書かれているか**。「B と比較して A にした。理由は〜」の形になっているか
- 検討した代替案があるなら、採否の理由が書かれているか
- 「だから」「そのため」でつながる 2 文が、実際に因果でつながっているか
- 前半の記述と後半の記述が整合しているか

### 説明の順序

- 用語を使う前に定義しているか
- 抽象的な説明の後に、必要な具体例があるか
- コードブロックの前に目的、後に読みどころの説明があるか
- 最小例から実用例へ進む過程で、必要な概念をすべて示しているか

### 締め

- `## おわりに` が本文の結論を回収しているか
- 結果と、読者に持ち帰ってほしいことが書かれているか
- 締めの内容が本文の範囲に収まっているか

### 構成の指針を満たしているか

`.claude/skills/blog-writing/references/structure.md` の「構成を決めるときの指針」と照らす。特に次を確認する。

- 背景を先に置き、読者が手順へ進む前に文脈を渡せているか
- 代替案を検討したなら、採否の理由が書かれているか
- 結果や結論が早い段階で出ているか
- うまくいかなかったことが書かれているか
- 前提条件 (環境、バージョン、自分の状況) が手順の前に開示されているか

**構成は題材が決める。** テンプレートとの一致そのものを指摘の根拠にせず、読者の理解に実際に影響が出ている箇所だけを挙げる。

## 出力

```
#### [ラベル] 短い指摘タイトル
- 観点: 構成・論理展開
- 箇所: <ファイルパス>:<行番号 または 行範囲>
- 影響: <読者の理解にどう影響するか>
- 根拠: <なぜ問題と言えるか。該当箇所を引用する>
- 改善案: <具体的にどう直すか>
```

ラベルは `must` (論理が破綻していて意味が通らない) / `should` (読みにくい・構成の問題) / `nits` (些末) / `question` (意図の確認) から選ぶ。

## 注意

- **構成の指摘は 3〜5 件に絞る。** 件数を絞るほど、本当に直すべき箇所が伝わる
- 見るのは、主張が論理的に支えられているかどうかとする。主張そのものへの賛否は対象外
- 「余談」「ちなみに」で本筋から外れる補足は**筆者の意図的なスタイル**として扱う
- 長さは題材が決めるものとして扱う
