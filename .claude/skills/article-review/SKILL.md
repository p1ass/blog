# Article Review

blog.p1ass.com の記事を、プロの編集者の視点からレビューする。

**基本動作はレビューのみとする。** ファイルの修正は、ユーザーから明示的な依頼があった場合のみ行う。

## Step 1: 対象の特定

引数からレビュー対象を特定する。

- スラッグが渡された場合: `app/routes/posts/<スラッグ>/index.mdx`
- ファイルパスが渡された場合: 指定されたファイル
- 何も渡されなかった場合: `git status` や `git diff` から変更中の `.mdx` を探す。複数見つかった場合はユーザーに確認する

対象ファイルの全文を読む。あわせて `.claude/skills/blog-writing/references/style.md` も読み、筆者の文体プロファイルを把握する。

## Step 2: textlint の実行

```bash
pnpm exec textlint "<対象ファイル>"
```

textlint が未インストールの場合は、先に `pnpm install` を実行する。実行できない場合はその旨を報告した上で、手動レビューへ進む。

## Step 3: 並列レビューの実行

3 つの観点それぞれについて、専門の subagent を**並列で**起動する。

| 観点 | Agent 指示ファイル | 目的 |
|---|---|---|
| 誤字脱字・表記 | `agents/typo.md` | 誤字脱字、表記ゆれ、送り仮名、日本語の誤りの検出 |
| 構成・論理展開 | `agents/structure.md` | 見出し構成、論理展開、説明順序、読者の理解しやすさの検証 |
| 文体逸脱 | `agents/style-drift.md` | 文体プロファイルからの逸脱、AI 特有表現の検出 |

subagent の起動プロンプトに含める項目:

- 対象ファイルの絶対パス
- 記事の全文
- 該当する agent 指示ファイルのパス、および指示ファイルを読んでから作業を進める旨の指示
- `.claude/skills/blog-writing/references/style.md` のパス
- `references/editorial-checklist.md` のパス
- 後述の「指摘の対象外」リスト

subagent 起動のプロンプト例:

```
blog.p1ass.com の記事を「{観点名}」の観点からレビューしてください。

まず .claude/skills/article-review/agents/{観点}.md を読み、レビュー指示に従ってください。
あわせて .claude/skills/article-review/references/editorial-checklist.md と
.claude/skills/blog-writing/references/style.md も読んでください。

## レビュー対象
- ファイル: {絶対パス}

## 記事本文
{全文}

確信度が高く、明確な根拠を示せる指摘のみを報告してください。
```

## Step 4: 結果のマージと出力

すべての subagent によるレビュー結果と textlint の出力を収集する。

1. 重複を排除する: 複数の subagent が同じ箇所を指摘している場合は 1 つに統合する
2. 重要度順に並べ替える: `must` → `should` → `nits` → `question` の順とし、重要度が同じ場合は行番号順とする
3. 確信度で絞り込む: 明確な根拠を示せている指摘のみを残す

### ラベル

| ラベル | 用途 |
|---|---|
| **must** | 公開前に必ず修正すべき点。事実誤認につながる誤字、筋の通らない論理、意味が通らない文 |
| **should** | 修正を推奨する点。読みにくさ、構成上の問題、表記ゆれ |
| **nits** | 軽微な指摘。修正するかどうかは任意 |
| **question** | 意図の確認。誤りかどうか判断がつかない箇所 |

### 出力フォーマット

各指摘は以下のフォーマット（観点・箇所・影響・根拠・改善案）で記述する。**明確な根拠を示せる指摘のみを報告する。**

```markdown
## Article Review

対象: app/routes/posts/<slug>/index.mdx
レビュー観点: 誤字脱字・表記 / 構成・論理展開 / 文体逸脱

### textlint の指摘

<行番号と修正案。問題がなければ「指摘なし」>

### 手動レビュー

#### [must] 「事前審査」と「本審査」が入れ替わっている
- 観点: 誤字脱字・表記
- 箇所: `app/routes/posts/example/index.mdx:42`
- 影響: 読者が手順を誤って理解する。この記事の中心的な主張に関わる
- 根拠: 38 行目では「事前審査 → 本審査」の順で説明しているが、42 行目では逆になっている
- 改善案: 「本審査を通してから物件を探す」→「事前審査を通してから物件を探す」

#### [should] 節の中で 2 つのことを説明している
- 観点: 構成・論理展開
- 箇所: `app/routes/posts/example/index.mdx:60-95`
- 影響: 読者がどちらの話を読んでいるか分からなくなる
- 根拠: 60-75 行が設定方法、76-95 行がトラブルシューティングで、独立した内容が 1 つの `##` に入っている
- 改善案: `### トラブルシューティング` として節を分ける
```

指摘事項がない場合はその旨を明記する。前置きや挨拶は省き、**出力は指摘事項のみとする。**

## 指摘の対象外

以下はこのブログの規約または意図的な記法であるため、指摘の対象外とする。

- `{/* <!--more--> */}`: 記事一覧で要約を区切るためのマーカー（全記事に配置されている）
- `<ExLinkCard url="..." />` `<Twitter url="..."/>` `<BlockLink href="...">` `<Note>`: このブログ独自の MDX コンポーネント
- 画像直下の `_キャプション_`: キャプション用のスタイルを適用するために `em` を用いる独自記法
- `<Twitter>` の URL が `twitter.com` であること: コンポーネントがこのドメイン形式を期待しているため
- `.claude/skills/blog-writing/references/style.md` に定義された筆者固有のスタイル（ですます調、一人称「私」、余談を挟む書き方など）
- `<!-- TODO: ... -->` コメント: 執筆中の未確定箇所を示す意図的なマーカー

## 修正の適用

ユーザーから修正の依頼があった場合のみ、ファイルを変更する。

- 論旨や構成、筆者の意見に影響を与える修正は、適用前に必ずユーザーと合意を取る
- 指摘を反映した後、日本語表現の推敲は `agy-polish` スキルで行う
- 修正適用後は textlint を再実行し、変更箇所と実行結果を報告する
