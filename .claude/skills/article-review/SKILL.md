# Article Review

blog.p1ass.com の記事を、プロの編集者の視点でレビューする。

**既定の動作はレビューのみとする。** ファイルの修正はユーザーが明示的に依頼した場合に行う。

## Step 1: 対象の特定

引数からレビュー対象を決める。

- スラッグが渡された場合: `app/routes/posts/<スラッグ>/index.mdx`
- ファイルパスが渡された場合: そのファイル
- 何も渡されなかった場合: `git status` と `git diff` で変更中の `.mdx` を探す。複数あれば確認する

対象ファイルを全文読む。あわせて `.claude/skills/blog-writing/references/style.md` を読み、筆者の文体プロファイルを把握する。

## Step 2: textlint の実行

```bash
pnpm exec textlint "<対象ファイル>"
```

textlint が未インストールの場合は `pnpm install` を先に実行する。実行できない場合はその旨を報告し、手動レビューに進む。

## Step 3: 並列レビューの実行

3 観点について、それぞれ専門の subagent を**並列で**起動する。

| 観点 | Agent指示ファイル | 目的 |
|---|---|---|
| 誤字脱字・表記 | `agents/typo.md` | 誤字脱字、表記ゆれ、送り仮名、日本語の誤り |
| 構成・論理展開 | `agents/structure.md` | 見出し構成、論の流れ、説明の順序、読者の理解 |
| 文体逸脱 | `agents/style-drift.md` | 文体プロファイルからのずれ、AI っぽさ |

subagent 起動時に含めること:

- 対象ファイルの絶対パス
- 記事の全文
- 該当する agent 指示ファイルのパスと、それを読んでから作業する指示
- `.claude/skills/blog-writing/references/style.md` のパス
- `references/editorial-checklist.md` のパス
- 後述の「指摘してはいけないもの」

subagent 起動のプロンプト例:

```
blog.p1ass.com の記事を「{観点名}」の観点からレビューしてください。

まず .claude/skills/article-review/agents/{観点}.md を読み、レビュー指示に従ってください。
あわせて .claude/skills/article-review/references/editorial-checklist.md と
.claude/skills/blog-writing/references/style.md も読んでください。

## レビュー対象
- ファイル: {絶対パス}

## 記事本文
{全文}

確信度の高い指摘のみ報告してください。根拠を書けた指摘だけを報告してください。
```

## Step 4: 結果のマージと出力

すべての subagent の結果と textlint の出力を収集する。

1. 重複を排除する。複数の subagent が同じ箇所を指摘している場合は統合する
2. 重要度順に並べ替える。`must` → `should` → `nits` → `question` の順とし、同じ重要度では行番号順にする
3. 確信度で絞る。根拠を書けた指摘だけを残す

### ラベル

| ラベル | 用途 |
|---|---|
| **must** | 公開前に必ず直す。事実誤認につながる誤字、論理の破綻、意味が通らない文 |
| **should** | 直すことを推奨。読みにくさ、構成の問題、表記ゆれ |
| **nits** | 些末な指摘。対応は任意 |
| **question** | 意図の確認。誤りかどうか判断できない箇所 |

### 出力フォーマット

各指摘は必ず 4 行構造で書く。**根拠を書けた指摘だけを報告する。**

```markdown
## Article Review

対象: app/routes/posts/<slug>/index.mdx
レビュー観点: 誤字脱字・表記 / 構成・論理展開 / 文体逸脱

### textlint の指摘

<行番号と修正案。問題がなければ「指摘なし」>

### 手動レビュー

#### [must] 「事前審査」と「本審査」が入れ替わっている
- 観点: 誤字脱字・表記
- 箇所: `app/routes/posts/example/index.mdx:42`
- 影響: 読者が手順を誤って理解する。この記事の中心的な主張に関わる
- 根拠: 38 行目では「事前審査 → 本審査」の順で説明しているが、42 行目では逆になっている
- 改善案: 「本審査を通してから物件を探す」→「事前審査を通してから物件を探す」

#### [should] 節の中で 2 つのことを説明している
- 観点: 構成・論理展開
- 箇所: `app/routes/posts/example/index.mdx:60-95`
- 影響: 読者がどちらの話を読んでいるか分からなくなる
- 根拠: 60-75 行が設定方法、76-95 行がトラブルシューティングで、独立した内容が 1 つの `##` に入っている
- 改善案: `### トラブルシューティング` として節を分ける
```

指摘がない場合はその旨を書く。**出力は指摘事項のみとする。**

## 指摘の対象外

次はこのブログの規約または意図的な記法なので、指摘の対象から外す。

- `{/* <!--more--> */}`: 記事一覧の要約を切るマーカー。全記事に入っている
- `<ExLinkCard url="..." />` `<Twitter url="..."/>` `<BlockLink href="...">` `<Note>`: このブログの MDX コンポーネント
- 画像直下の `_キャプション_`: `em` をキャプション用にスタイルしている独自の使い方
- `<Twitter>` の URL が `twitter.com` であること: コンポーネントがこの形式を期待している
- `.claude/skills/blog-writing/references/style.md` に定義された筆者固有のスタイル (ですます調、一人称「私」、余談を挟む書き方など)
- `<!-- TODO: ... -->` コメント: 執筆中の未確定箇所を示す意図的なマーカー

## 修正の適用

ユーザーが修正を依頼した場合だけファイルを変更する。

- 論旨、構成、筆者の意見を変える修正は、適用する前に合意を取る
- 適用後は textlint を再実行し、変更箇所と結果を報告する
