# Blog Writing

blog.p1ass.com の記事を執筆する。文体は筆者 p1ass のスタイルに準拠し、内容の正確性は事実確認（裏取り）の徹底によって担保する。

このスキルは、**文体の一貫性**と**事実の確からしさ**を担保することを目的としている。この 2 点を徹底するためであれば、執筆に時間をかけて構わない。

## 大原則

1. **裏付けが取れた事実だけを書く**。確認が済んでいない箇所は `<!-- TODO: 要確認 -->` として残す。
2. **本文はメインエージェントが一貫して書く**。並列化の対象は事実確認（裏取り）のみとする。節ごとに subagent へ分担させると文体の一貫性が損なわれる
3. **`index.mdx` への書き出しで完了とする**。コミットや公開のタイミングは筆者（ユーザー）自身が判断する。

## ワークフロー

### Step 1: 題材の確認

記事のテーマ（何について書くか）を確定させ、大まかな構成の見通しを立てる。

[`references/structure.md`](references/structure.md) を参照し、次の事項を判断する。

- 読者が記事を読み終えたときに何ができるようになるか（達成基準）
- 既に手元にある材料（実装したコード、実行ログ、スクリーンショット、計測スコアなど）
- 題材に適した構成。構成は題材に応じて決まるため、固定のテンプレートに無理に合わせるのではなく、題材に適した自然な流れを優先する

題材が曖昧な場合は AskUserQuestion で質問する。疑問点が解消されるまで対話を重ね、題材を明確に固めてから次のステップに進む。

### Step 2: 事実の裏取り（subagent による並列実行）

記事内で言及する事実や主張を洗い出し、**subagent を並列起動して**裏付けを取る。この工程が記事全体の信頼性を左右する。

まず検証すべき主張を列挙し、それぞれどの手段で確認するかを割り振る。確認手段が独立している主張は、並列で検証を進める。

| 手段                                         | 対象                                                               |
| -------------------------------------------- | ------------------------------------------------------------------ |
| 公式ドキュメント・仕様・リリースノートの確認 | API の挙動、オプション名、対応バージョン、非推奨の状況             |
| リポジトリ内のコード確認                     | 自身の実装、設定ファイル、実際に動作しているコード                 |
| コマンド実行による検証                       | バージョン番号、実際のコマンド出力、ビルドの成否、ベンチマーク結果 |

subagent の起動プロンプトに含める事項:

- 検証してほしい主張 (「Hono の JSX Renderer は〇〇できる」のように、真偽を判定できる明確な命題にする)
- 確認手段の指定 (URL、ファイルパス、実行すべきコマンド)
- **一次情報のリンク先を実際に参照して確認すること**の指示
- 出力形式: 主張 / 確認結果 (真偽) / 根拠 (URL、ファイルパス、コマンドと実行結果) / 補足

裏付けが取れなかった主張は本文に採用しないか、残す場合は `<!-- TODO: 要確認 -->` のコメントを付与する。**言い切る形で書けるのは、十分に裏付けが取れた主張のみとする。**

### Step 3: アウトラインの提示と合意

見出し構成を提示し、合意を形成してから本文の執筆に進む。構成をあらかじめ固めておくことで、手戻りや大幅な書き直しを防ぐことができる。

提示する内容:

- 見出し（`##` / `###`）の一覧
- 各節で記述する内容の 1 行要約
- 各節に必要な材料（コード、画像、外部リンクなど）とその調達状況
- Step 2 で裏付けが取れなかった箇所（未確定事項）

### Step 4: 本文の執筆

[`references/style.md`](references/style.md) と [`references/mdx-conventions.md`](references/mdx-conventions.md) を事前に確認してから執筆に入る。

節ごとに執筆を進め、都度ユーザーの確認（レビュー）を受ける。**文体の一貫性を保つため、執筆はメインエージェントが一貫して担当する。**

### Step 5: 書き出し

`app/routes/posts/<slug>/index.mdx` にファイルを書き出す。

- slug は英小文字とハイフンのみで構成し、記事の内容が推測できる簡潔な単語にする（例: `migrate-to-hono`、`go-base62`、`keep-inbox-empty`）
- 画像は同じディレクトリに配置する前提でパスを記述し、ファイル自体はプレースホルダーとして残しておく
- frontmatter の `categories` や `tags` は [`references/taxonomy.md`](references/taxonomy.md) に定義された既存の語彙から選択する。新しいカテゴリやタグを追加する場合は、必ず事前にユーザーへ確認する

### Step 6: レビューと校正

以下の観点からレビューと校正を実施し、検出された指摘をもとに文章を修正する。

1. `tech-review` スキルを実行し、技術的正確性、一次情報の確認、再現性、リスクを検証する
2. `article-review` スキルを実行し、誤字脱字、構成、文体プロファイルからの逸脱を検証する
3. `japanese-technical-writing` スキルを参照し、冗長表現の排除、文末表現の重複回避、漢字とひらがなの使い分けを徹底する
4. textlint を実行し、機械的な校正や AI らしい不自然な表現（`@textlint-ja/preset-ai-writing`）を検出する
5. 検出された指摘事項をもとに文章を修正する
6. `agy-polish` スキルを実行し、日本語として自然な表現に推敲する

```bash
pnpm exec textlint "app/routes/posts/<slug>/index.mdx"
```

## サブモード

基本のワークフローは上記の Step 1〜6 だが、ユーザーの依頼内容に応じて以下のモードで柔軟に動作する。

| モード           | 動作                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| 全文ドラフト     | Step 3 のアウトライン合意を省略し、Step 4 の本文執筆まで一気に進める。急ぎでドラフトを作成したい場合に使用する |
| 推敲のみ         | 既存の下書きに対して文体プロファイルの適用や校正（Step 6、`agy-polish` を含む）を行い、`index.mdx` に書き出す  |
| アウトラインのみ | Step 3（アウトラインの作成・提示）で終了する。題材や全体の構成を固める段階で使用する                           |

## 文体の核

詳細は [`references/style.md`](references/style.md) を参照すること。最低限そろえる要点は次の 9 点とする。

- ですます調に統一し、一人称は「私」を使用する
- **書き言葉を徹底する**。口語表現や絵文字は避ける
- 余談や率直な自己開示は残す。失敗談や具体的な数値をそのまま記述する
- 半角英数と日本語の間には半角スペースを入れる
- 改行は表示結果（レンダリング）を基準にする。スマートフォン表示で文字が詰まって見えないよう適切に区切る
- 肯定形で書く。同じ内容を肯定表現で書ける場合は、そちらを選択する
- 太字による強調は要所のみに絞る。1 記事につき数カ所程度にとどめる
- 見出しは名詞句か短い 1 文で完結させる。ダッシュ等でサブタイトルを追加しない
- 締めの見出しは `## おわりに` で統一する
