# Blog Writing

blog.p1ass.com の記事を執筆する。文体は筆者 p1ass のもので、内容の正しさは裏取りで担保する。

このSkillは**文体の一貫性**と**事実の確からしさ**の2点を担保するために存在する。この2点を守るためなら、執筆に時間をかけてよい。

## 大原則

1. **裏取りできた事実だけを書く**。確認が済んでいない箇所は `<!-- TODO: 要確認 -->` として残す
2. **本文は本体が通しで書く**。並列化の対象は裏取りに限る。節ごとにsubagentへ分担させると文体が割れる
3. **`index.mdx` の書き出しで終える**。コミットと公開タイミングは筆者が決める

## ワークフロー

### Step 1: 題材の確認

何について書くのかを確定し、構成の当たりをつける。

[`references/structure.md`](references/structure.md) を読み、次を判断する。

- 読者が記事を読み終えたときに何ができるようになるのか
- 既に手元にある材料 (実装したコード、実行ログ、スクリーンショット、スコア)
- 題材に合う構成。構成は題材が決めるので、テンプレートに寄せるより題材に合う流れを優先する

題材が曖昧な場合はここで質問する。題材を固めてから裏取りに進むことで、調べ直しを避けられる。

### Step 2: 事実の裏取り (subagentで並列実行)

記事で主張する事実を洗い出し、**subagentを並列起動して**裏を取る。この工程が記事の信頼性を決める。

まず主張を列挙し、それぞれをどの手段で確認するか割り当てる。手段が独立している主張は並列で走らせる。

| 手段 | 対象 |
|---|---|
| 公式ドキュメント・仕様・リリースノートの取得 | API の挙動、オプション名、対応バージョン、非推奨の状況 |
| リポジトリの実コード確認 | 自分の実装、設定ファイル、実際に動いているコード |
| コマンド実行 | バージョン番号、実際の出力、ビルドの成否、ベンチマーク結果 |

subagent起動時に含めること:

- 確認してほしい主張 (「Hono の JSX Renderer は〇〇できる」のように、真偽が判定できる形で書く)
- 確認手段の指定 (URL、ファイルパス、実行すべきコマンド)
- **一次情報のリンク先を実際に開いて読むこと**の指示
- 出力形式: 主張 / 確認できたか / 根拠 (URL・ファイルパス・コマンドと出力) / 補足

裏が取れなかった主張は捨てるか、`<!-- TODO: 要確認 -->` を付けて記事に残す。**断定形で書けるのは裏が取れた主張だけとする。**

### Step 3: アウトラインの提示と合意

見出し構成を提示し、合意を取ってから本文に進む。構成を先に固めることで、書き直しの範囲を小さく保てる。

提示するもの:

- 見出し (`##` / `###`) の一覧
- 各節で書く内容の1行要約
- 各節に必要な材料 (コード、画像、外部リンク) と、その調達状況
- Step 2 で裏が取れなかった箇所

### Step 4: 本文の執筆

[`references/style.md`](references/style.md) と [`references/mdx-conventions.md`](references/mdx-conventions.md) を読んでから書く。

節ごとに書き、都度レビューを受ける。**執筆は本体が通しで担当する。**

### Step 5: レビューと校正

次の4つをすべて実施する。

1. `tech-review` Skill を呼ぶ (技術的正確性・一次情報・再現性・リスク)
2. `article-review` Skill を呼ぶ (誤字脱字・構成・文体逸脱)
3. `japanese-technical-writing` Skill を参照する (冗長表現、文末の繰り返し、漢字とひらがなの使い分け)
4. textlint を実行する

```bash
pnpm exec textlint "app/routes/posts/<slug>/index.mdx"
```

AI っぽさが気になる場合は `natural-japanese` Skill も参照する。

### Step 6: 書き出し

`app/routes/posts/<slug>/index.mdx` に書き出す。

- slug は英小文字とハイフンのみ。記事内容が推測できる短い語にする (`migrate-to-hono`、`go-base62`、`keep-inbox-empty`)
- 画像は同じディレクトリに置く前提でパスを書き、ファイル自体はプレースホルダとして残す
- frontmatter の `categories` / `tags` は [`references/taxonomy.md`](references/taxonomy.md) の既存語彙から選ぶ。新語を作る場合は必ず確認を取る

**ここで作業を終える。** 書き出したファイルのパスと、残っている TODO を報告する。コミットは筆者に任せる。

## サブモード

既定は上記の Step 1〜6 だが、依頼に応じて次のモードで動く。

| モード | 動き |
|---|---|
| 全文ドラフト | Step 3 のアウトライン合意を省略し、Step 4 まで一気に進む。急ぐときに使う |
| 推敲のみ | 既存の下書きに対して Step 5 だけを実施する。文体プロファイルへの寄せも行う |
| アウトラインのみ | Step 3 で止める。題材を固める段階で使う |

## 文体の核

詳細は [`references/style.md`](references/style.md) にある。最低限そろえるのは次の9点。

- ですます調、一人称は「私」
- **書き言葉で通す**。口語表現と絵文字を避ける
- 余談と率直な自己開示は残す。失敗も具体的な数字もそのまま書く
- 半角英数と日本語の間に半角スペースを入れる
- 改行はレンダリング結果基準。スマホで文字がびっしりに見えないよう区切る
- 導入は `こんにちは、ぷらす([@p1ass](https://x.com/p1ass))です。`
- 肯定形で書く。同じ内容を肯定形で書けるなら、そちらを選ぶ
- 見出しは名詞句か短い文ひとつで完結させる。ダッシュでサブタイトルを足さない
- 締めの見出しは `## おわりに`
