# 一次情報の裏取りレビュー

記事中の事実に関する主張を洗い出し、一次情報で裏付けが取れるかを確認する。

**一次情報のリンク先を必ず開いて読む。** 検索結果の要約は出発点として扱う。

## 手順

### 1. 主張を洗い出す

記事を読み、真偽が判定できる形の主張を列挙する。

- API の挙動、オプション名、デフォルト値
- 対応バージョン、非推奨や削除の状況
- 仕様上の規範的な記述 (「〜しなければならない」「〜は保証される」)
- 性能や制限に関する数値
- 「〜できない」「〜は存在しない」といった主張 (**特に慎重に確認する**)

### 2. 一次情報で確認する

優先順位の高い順に当たる。

1. 仕様書、RFC、言語仕様
2. 公式ドキュメント
3. 公式リポジトリのソースコード、リリースノート、CHANGELOG
4. 標準化の議論、公式の Issue や Discussion

一次情報として扱うのは上記 4 つとする。個人ブログや Stack Overflow のみを根拠とする主張は `question` として報告する。

### 3. 区別する

次の区別ができているかを確認する。

- **規範的要件** (仕様が要求すること) と **実装固有の挙動** (特定の処理系がそうしているだけ)
- **現在の仕様** と **過去の提案・議論**
- **事実** と **筆者の推測・意見**

「〜だからこうなっている」という説明について、資料に根拠があるかを確認する。

### 4. 引用の整合を見る

- 記事が貼ったリンク先はその近くの主張を実際に裏付けているか
- 引用文が原典と一致し、文脈を保っているか
- `<ExLinkCard>` の URL が生きているか

## 特に注意する箇所

### バージョン依存の記述

記事の執筆時点と現在で状況が変わっている場合がある。次は必ず現在の資料で確認する。

- ライブラリやフレームワークのバージョン番号
- ベータ・実験的機能の現在の状況 (GA になったか、削除されたか)
- `@beta` `@next` のようなタグ付きバージョン
- クラウドサービスの料金、制限値、リージョン

### 不在を述べる主張

「〜はできない」「〜というオプションはない」という主張は根拠の確認が省かれがちなので、ドキュメントを検索して実在の有無を確かめる。実在した場合は `must` とする。

### 過去記事の場合

過去に書かれた記事には当時は正しく、現在は変わっている記述が含まれる。その場合は「執筆時点では正しかったものの現在は変わっている」と明記して報告し、`should` 以下とする。

## 出力

```
#### [ラベル] 短い指摘タイトル
- 観点: 一次情報の裏取り
- 箇所: <ファイルパス>:<行番号>
- 影響: <読者にどう影響するか>
- 根拠: <一次情報の URL と、そこに書かれている内容。実行したコマンドがあればその出力>
- 改善案: <具体的な修正、または追加すべき記述>
```

ラベルは `must` (事実誤認) / `should` (根拠不足、バージョンの書き落とし) / `nits` (補足があるとよい) / `question` (判断に筆者の情報が必要) から選ぶ。

## 報告に含めること

確認できなかった主張を必ず列挙する。裏取りの範囲を明示することが報告の一部となる。

- どの主張が確認できなかったか
- 確認できなかった理由 (一次情報が見つからない、認証が必要、など)
