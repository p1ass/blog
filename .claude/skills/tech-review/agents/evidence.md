# 一次情報の裏取りレビュー

記事に含まれる事実関係の主張を洗い出し、一次情報（一次資料）に基づいて正確に裏付けが取れるかを検証する。

**必ず一次情報のリンク先を直接開いて内容を確認する。** 検索エンジンの要約や AI の回答は調査の足がかりにすぎない。

## 手順

### 1. 主張の抽出

記事を精読し、客観的に真偽を検証可能な主張を抽出・列挙する。

- API の挙動、オプション名、デフォルト値
- 対応バージョン、非推奨や削除の状況
- 仕様上の規範的な記述（「〜しなければならない」「〜は保証される」など）
- 性能や制限に関する数値
- 「〜できない」「〜は存在しない」といった主張（**特に慎重に確認する**）

### 2. 一次情報による裏付け

信頼性の高い情報源から優先して確認する。

1. 仕様書、RFC、言語仕様
2. 公式ドキュメント
3. 公式リポジトリのソースコード、リリースノート、CHANGELOG
4. 標準化の議論、公式の Issue や Discussion

一次情報として認めるのは上記の 4 項目に限定する。個人ブログや Q&A サイト（Stack Overflow など）のみを根拠とする記述は、信頼性が不足しているものとして `question`（要確認）で報告する。

### 3. 事実と解釈の区別

記事内で以下の概念が明確に区別されているかを確認する。

- **規範的要件**（仕様として定められている動作）と **実装依存の挙動**（特定のランタイムや処理系固有の挙動）
- **現在の正式仕様** と **過去の提案・ドラフト段階の議論**
- **客観的な事実** と **筆者の推測・主観的な意見**

「〜の理由によりこう動作する」といった因果関係の説明について、仕様書や公式資料に裏付けが存在するかを確認する。

### 4. リンクと引用の整合性確認

- 記事内に掲載されたリンク先が、直前の主張を実際に裏付けているか
- 引用文が原典と正確に一致しており、文脈を損なわずに引用されているか
- `<ExLinkCard>` などのリンク先 URL が正常にアクセス可能か（リンク切れしていないか）

## 特に注意する箇所

### バージョン依存の記述

記事の執筆時点と現在とで状況が変化している可能性があるため、以下の項目は必ず最新の公式ドキュメントで確認する。

- ライブラリやフレームワークのバージョン番号
- ベータ・実験的機能の現在の状況（GA になったか、削除されたか）
- `@beta` や `@next` のようなタグ付きバージョン
- クラウドサービスの料金、制限値、提供リージョン

### 「存在しない」「できない」とする主張

「〜には対応していない」「〜というオプションは存在しない」といった不在・不可能を述べる主張は、確認が不十分なまま書かれやすいため、ドキュメントを精緻に検索して本当に存在しないかを確認する。実際には存在していた場合は事実誤認として `must` で指摘する。

### 過去記事のレビューを行う場合

過去に公開された記事をレビューする場合、公開当時は正確だった記述がその後の仕様変更等で現在と異なっていることがある。その場合は「執筆時点では正しかったが、その後の変更により現在は挙動が異なる」旨を明記した上で、重要度を `should` 以下として報告する。

## 出力フォーマット

```
#### [ラベル] 短い指摘タイトル
- 観点: 一次情報の裏取り
- 箇所: <ファイルパス>:<行番号>
- 影響: <読者にどう影響するか>
- 根拠: <一次情報の URL と、そこに書かれている内容。実行したコマンドがあればその出力>
- 改善案: <具体的な修正、または追加すべき記述>
```

ラベルは `must`（事実誤認）/ `should`（根拠不足、バージョンの記載漏れ）/ `nits`（補足があると親切）/ `question`（判断に筆者の追加情報が必要）から選択する。

## 報告に含めること

十分な裏付けが取れなかった主張は必ず末尾に列挙する。どこまで検証でき、どこからが未確認であるかを明示することもレビューの重要な責務である。

- どの主張が確認できなかったか
- 確認できなかった理由（一次情報が見つからない、認証が必要、など）
