# リスクと互換性のレビュー

読者がこの記事の通りに手を動かしたときに起こる、望ましくない結果を洗い出す。

## 見るもの

### 秘密情報の露出

**最優先で確認する。見つけた場合は必ず `must` とする。**

記事本文、コードブロック、コマンドの出力例、スクリーンショットの中を確認する。

- API キー、トークン、パスワード、秘密鍵
- `.env` の中身、認証情報を含む接続文字列
- 実在する内部ホスト名、非公開 URL、社内のリポジトリ名やパス
- 個人を特定できる情報 (メールアドレス、実名、電話番号)
- スクリーンショット内に写り込んだ上記

プレースホルダになっているか (`YOUR_API_KEY`、`${{ secrets.XXX }}`、`example.com`) を確認する。実在しそうな値は無効化済みであっても指摘する。

### セキュリティ上の危険な指南

記事が読者に勧めている操作の安全性を確認する。

- 認証や検証を無効化する設定 (`verify=False`、`--insecure`、CORS の全許可)
- 権限を過剰に与える設定 (`chmod 777`、ワイルドカードの IAM ロール、過剰な `sudo`)
- 入力の検証を省いて実行や埋め込みをするコード (コマンドインジェクション、SQL インジェクション)
- 秘密情報をログやリポジトリに残す手順
- 教育目的の簡略化として許容できる範囲を超えた省略

簡略化が意図的な場合は記事に注記があるかを確認する。注記のない危険な書き方は指摘する。

### 破壊的な操作

- 読者が実行するとデータが消える、または元に戻せないコマンド (`rm -rf`、`DROP`、`--force`、`git push --force`)
- 本番環境に影響する操作が、そうと分かる形で書かれているか
- 後始末の手順 (作ったリソースの削除、課金の停止) が書かれているか

クラウドリソースを作る記事で、**課金が発生することと、削除方法**が書かれているかを確認する。

### 互換性

- OS、ランタイム、ブラウザ、ライブラリのバージョン依存が正しく書かれているか
- 特定の環境 (macOS、Apple Silicon、特定のシェル) への依存が記事に明記されているか
- 実験的な API や不安定な依存関係が、記事の**早い段階で**示されているか
- 使っている機能が現行のものか (非推奨や削除予定でないか)

### 運用上の落とし穴

- 失敗したときに何が起きるか、どう復旧するかが書かれているか
- 前提条件が満たされない場合の挙動に触れているか
- スケール時に問題となる書き方 (N+1、無制限のリトライ、上限のないキャッシュ) に注記があるか

## 出力

```
#### [ラベル] 短い指摘タイトル
- 観点: リスクと互換性
- 箇所: <ファイルパス>:<行番号>
- 影響: <読者がこの通りにやると何が起きるか。具体的に書く>
- 根拠: <該当箇所の引用と、なぜ危険か。一次情報があれば URL>
- 改善案: <安全な書き方、または追加すべき注記>
```

ラベルは次の基準で選ぶ。

- `must`: 秘密情報の露出、読者のデータや環境を壊す手順、明確な脆弱性を教えている
- `should`: 危険な簡略化に注記がない、互換性の書き落とし、後始末の手順がない
- `nits`: あれば親切という程度の注意書き
- `question`: 意図的な簡略化かどうか判断できない

## 注意

- **指摘の対象はこの記事のこの箇所に実際に存在する問題に限る。** 一般的な注意喚起の列挙は避ける
- 判断基準は「読者がこの通りに真似して困るか」とする。求める水準を個人ブログの記事に見合わせる
- 記事が「検証用」「ローカル限定」と断っている箇所はその前提で評価する
