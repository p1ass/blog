# リスクと互換性のレビュー

読者が記事の記述通りに手を動かした際に生じる可能性のある、セキュリティリスク、環境破壊、互換性問題などの望ましくない影響を洗い出す。

## レビュー観点

### 秘密情報の露出

**最優先で検証する。該当箇所を発見した場合は必ず `must` とする。**

記事本文、コードブロック、コマンド実行結果の出力例、および掲載画像（スクリーンショット）内をくまなく確認する。

- API キー、トークン、パスワード、秘密鍵
- `.env` の中身、認証情報を含む接続文字列
- 実在する内部ホスト名、非公開 URL、社内のリポジトリ名や内部パス
- 個人を特定できる情報（メールアドレス、実名、電話番号など）
- スクリーンショット内に写り込んだ上記の情報

適切なプレースホルダー形式（`YOUR_API_KEY`、`${{ secrets.XXX }}`、`example.com` など）になっているかを確認する。実在し得る形式の値は、たとえ失効・無効化済みであっても露出とみなして指摘する。

### セキュリティ上の危険な指南

記事内で案内・推奨されている手順やコードの安全性を検証する。

- 認証や検証を無効化する設定（`verify=False`、`--insecure`、CORS の全許可など）
- 権限を過剰に与える設定（`chmod 777`、ワイルドカード指定の IAM ロール、過剰な `sudo` など）
- 入力の検証を省いて実行や埋め込みを行うコード（コマンドインジェクション、SQL インジェクションなど）
- 秘密情報をログやリポジトリに残す手順
- 解説用の簡略化として許容できる範囲を超えた、危険な実装の放置

コードの簡略化が解説上の意図的なものである場合は、その旨の注記や警告が記載されているかを確認する。注記のない危険なコード例は指摘の対象とする。

### 破壊的な操作

- 読者が実行するとデータ消失や不可逆な変更をもたらすコマンド（`rm -rf`、`DROP TABLE`、`--force` オプション、`git push --force` など）に対する注意喚起があるか
- 本番環境に影響を及ぼし得る危険な操作について、十分に注意喚起がなされているか
- 後始末の手順（作成したリソースの削除、課金の停止など）が明記されているか

クラウド上のリソースを作成・プロビジョニングする記事では、**課金が発生する旨の注意喚起と、検証後のリソース削除手順**が記載されているかを確認する。

### 互換性

- OS、ランタイム、ブラウザ、ライブラリのバージョン依存関係が正確に記載されているか
- 特定の環境（macOS、Apple Silicon、特定のシェルなど）への依存が記事に明記されているか
- 実験的な API や不安定な依存関係が、記事の**早い段階で**示されているか
- 利用している機能や構文が現行の標準であり、非推奨（deprecated）や廃止予定となっていないか

### 運用上の注意点

- 処理が失敗した際に何が起きるか、どう復旧するかが記載されているか
- 前提条件が満たされない場合の挙動に触れているか
- 負荷増や運用規模の拡大に伴って顕在化する問題（N+1 クエリ、バックオフのない無制限リトライ、サイズ上限のないキャッシュなど）に対して、必要な注記や補足がなされているか

## 出力フォーマット

```
#### [ラベル] 短い指摘タイトル
- 観点: リスクと互換性
- 箇所: <ファイルパス>:<行番号>
- 影響: <読者がこの通りに実行すると何が起きるか。具体的に書く>
- 根拠: <該当箇所の引用と、なぜ危険かの説明。一次情報があれば URL>
- 改善案: <安全な書き方、または追加すべき注記>
```

ラベルは次の基準で選択する。

- `must`: 秘密情報の露出、読者のデータや環境を破壊する手順、明確な脆弱性をもたらす指南
- `should`: 危険な簡略化に対する注記の欠落、互換性の記載漏れ、後始末手順の欠落
- `nits`: あれば親切という程度の補足・注意書き
- `question`: 意図的な簡略化かどうか判断できない事項

## 注意事項

- **指摘の対象は、対象記事の具体的な記述に直接起因する実際の問題に限定する。** 一般論としての注意喚起を無差別に列挙することは避ける
- 判断基準は「読者がこの記事の通りに真似をした結果、実害やトラブルが発生するか」とする。個人技術ブログとしての文脈や読者層に適した要求水準を見極める
- 記事内で「検証用」「ローカル限定」と明記されている箇所は、その前提を踏まえて評価する
