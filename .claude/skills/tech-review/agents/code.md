# コードと再現性のレビュー

記事のコードが動くか、手順を追って同じ結果になるかを検証する。

## 検証の優先順位

上から順に当たり、検証できた時点で打ち切ってよい。

1. **記事に対応する実際のプロジェクト**が手元にある場合、そこで記録されたコマンドを実行する
2. **リポジトリで既に利用できるテスト・ビルド・型検査**を動かす
3. **記事のコードと、実際に動いているコードの一致**を確認する (このブログの記事は自分の実装について書くことが多い。`git log` や実ファイルと突き合わせる)
4. 完全なサンプルがない場合、**独立して実行可能なコードブロックを検査する**

## Go コードの実行検証

Go は記事で最も多い言語 (`tags: Go` が 24 記事)。独立した Go のコードブロックはスクリプトで検証できる。

```bash
bash .claude/skills/tech-review/scripts/verify_go_samples.sh <記事ファイル>
```

スクリプトは記事から ```go のコードブロックを抽出し、`package` 宣言を持つ完結したものだけを一時ディレクトリに書き出して `go vet` と `go build` にかける。

**注意点**

- 使うのはインストール済みの `go` に限る。依存パッケージの取得やモジュールの追加はユーザーの承認を得てから行う
- 実行対象は破壊的な操作・認証情報・外部サービスへの接続を含まないコードに限る
- `package` 宣言を持たない断片は前後の文脈に依存するため、静的レビューに回す
- **単体実行の失敗は記事の誤りの候補として扱う。** 記事のコードブロックには意図的な省略が含まれる
- **構文チェックの結果は構文の正しさの範囲で扱う**

## Go 以外の言語

Caddyfile、YAML、Protocol Buffers、mermaid、シェルスクリプトは文脈に依存するため、静的にレビューする。

- 構文が正しいか (インデント、クォート、括弧の対応)
- 使われているディレクティブやフィールドが実在するか (一次情報で確認)
- 記事内の他のコードブロックと整合しているか
- mermaid は構文のみを見る。図の内容の妥当性は構成の問題として `article-review` に任せる

## 静的レビューで見るもの

### コードそのもの

- 構文、型、制御フロー、API の使い方が対象バージョンで正しい
- import、依存関係、環境変数、設定がそろい、コード中の変数がすべて定義されている
- エラーハンドリングが記事の主旨に照らして適切である (教育目的の省略は許容し、危険な省略を指摘する)

### 手順の再現性

- コマンドを実行するディレクトリを明記している
- 前提となるセットアップ (インストール、認証、設定ファイル) が記事に書かれている
- コマンドの順序が正しい。後のステップが前のステップの成果物に依存している場合、その依存が明示されている
- 期待される出力が書かれており、実際の出力と一致する

### 検証環境

- OS、言語バージョン、ライブラリバージョンが記事に書かれている
- 「動きました」の根拠となる環境を特定できる
- 単一環境の結果を、その環境での結果として提示している

### 記事内の整合

- 同じコードが複数箇所に出てくる場合、内容が一致している
- 本文中の説明とコードが一致している (「3 回リトライする」と書いた箇所のコードが 3 回になっているか)
- コードブロック内のコメントと実際の処理が一致している

## 出力

```
#### [ラベル] 短い指摘タイトル
- 観点: コードと再現性
- 箇所: <ファイルパス>:<行番号 または 行範囲>
- 影響: <読者がこの通りに実行するとどうなるか>
- 根拠: <実行したコマンドとその出力、または一次情報の URL>
- 改善案: <具体的な修正コードまたは追加すべき記述>
```

ラベルは `must` (動かない、結果が異なる) / `should` (バージョン未記載、手順の欠落) / `nits` (改善提案) / `question` (検証環境の確認が必要) から選ぶ。

## 報告に含めること

- 実行したコマンド、環境、結果
- 実行できなかったコードブロックと、その理由
- 静的レビューにとどめた箇所
