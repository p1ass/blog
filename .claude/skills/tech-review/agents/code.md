# コードと再現性のレビュー

記事に掲載されているコードが正常に動作するか、読者が手順通りに実行して同じ結果を再現できるかを検証する。

## 検証の優先順位

優先度の高い順（1 から順）に確認し、十分に検証できた時点で以降の確認を省略してよい。

1. **記事の元となった実プロジェクトのリポジトリ**が手元にある場合は、そこで記録されているコマンドを実行して動作を確認する
2. **リポジトリに用意されているテスト・ビルド・型チェック**を実行する
3. **記事中のコードと実際に動作しているコードの一致**を確認する（当ブログの記事は自作の実装に関する内容が多いため、実ファイルの履歴や `git log` と突き合わせる）
4. 完全なプロジェクトがない場合は、**独立して実行可能なコードブロックを抽出して動作検証を行う**

## Go コードの実行検証

Go は当ブログで最も言及頻度の高い言語である（`tags: Go` が多数）。完結した Go のコードブロックは専用スクリプトを用いて検証できる。

```bash
bash .claude/skills/tech-review/scripts/verify_go_samples.sh <記事ファイル>
```

このスクリプトは、記事内の ```go コードブロックから `package` 宣言を含む完結したサンプルを抽出し、一時ディレクトリに書き出した上で `go vet` および `go build` を実行する。

**注意点**

- ローカル環境にインストール済みの `go` コマンドのみを使用する。外部依存パッケージの取得やモジュールの追加が必要な場合は、事前にユーザーの承認を得ること
- 破壊的操作、認証情報の使用、外部サービスへの通信を含まないコードのみを実行対象とする
- `package` 宣言を持たないコード断片は前後の文脈に依存するため、動的実行ではなく静的レビューで検証する
- **単体実行の失敗は直ちに誤りと断定せず、誤りの「候補」として慎重に扱う**（記事上のコードブロックには、説明のために意図的な省略が含まれる場合があるため）
- **ビルドや構文チェックの成否は、あくまで構文やコンパイルの妥当性を保証するものとして扱い、ロジック自体の正しさは別途確認する**

## Go 以外の言語

Caddyfile、YAML、Protocol Buffers、Mermaid、シェルスクリプトなどは文脈への依存が強いため、静的レビューで検証する。

- 構文が正しいか（インデント、クォート、括弧の対応など）
- 使用されているディレクティブや設定項目、フィールドが実在するか（公式ドキュメント等の一次情報で確認）
- 記事内の他のコードブロックや設定内容と整合しているか
- Mermaid は構文の正しさのみを確認する。図が示す内容や論理構成の妥当性は、文章・構成のレビューとして `article-review` に任せる

## 静的レビューの検証項目

### コードそのもの

- 構文、型定義、制御フロー、API の呼び出し方が対象バージョンにおいて正しいか
- 必要な import、依存関係、環境変数、設定が揃っており、参照されている変数がすべて定義されているか
- エラーハンドリングが記事の趣旨に照らして適切か（解説目的の意図的な省略は許容し、読者がそのまま本番で真似すると危険な省略のみを指摘する）

### 手順の再現性

- コマンドを実行すべき作業ディレクトリが明記されているか
- 前提となる環境構築やセットアップ手順（ツールのインストール、認証、設定ファイルの作成など）が網羅されているか
- コマンドの実行順序が正しいか（後続ステップが先行ステップの成果物に依存する場合、その前提関係が明示されているか）
- 期待される実行結果やログが記載されており、実際の挙動と一致しているか

### 検証環境

- 検証時の OS、言語バージョン、主要ライブラリのバージョンが明記されているか
- 動作確認の根拠となる環境条件を読者が特定できるか
- 特定環境のみでの動作結果を、あたかも全環境で共通であるかのように一般化して書いていないか

### 記事内の整合性

- 同一のコードや設定が複数箇所に登場する場合、内容に不整合がないか
- 本文の説明とコードの実装内容が一致しているか（例: 本文で「3 回リトライする」と説明している場合、コード側のループ回数や設定値も 3 回になっているか）
- コードブロック内のコメントと実際の処理内容が一致しているか

## 出力フォーマット

```
#### [ラベル] 短い指摘タイトル
- 観点: コードと再現性
- 箇所: <ファイルパス>:<行番号 または 行範囲>
- 影響: <読者がこの通りに実行するとどうなるか>
- 根拠: <実行したコマンドとその出力、または一次情報の URL>
- 改善案: <具体的な修正コードまたは追加すべき記述>
```

ラベルは `must`（動かない、結果が異なる）/ `should`（バージョン未記載、手順の欠落）/ `nits`（改善提案）/ `question`（検証環境の確認が必要）から選択する。

## 報告に含めること

- 実行したコマンド、環境、検証結果
- 実行できなかったコードブロックと、その理由
- 静的レビューにとどめた箇所
