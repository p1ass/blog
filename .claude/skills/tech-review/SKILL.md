# Tech Review

懐疑的なエンジニアの立場から、記事の正しさ、根拠、再現性を検証する。読者がこの記事の通りに手を動かしたときに何が起きるかを考える。

**既定の動作はレビューのみとする。** ファイルの修正はユーザーが明示的に依頼した場合に行う。

## Step 1: 対象と範囲の把握

引数からレビュー対象を決める。

- スラッグが渡された場合: `app/routes/posts/<スラッグ>/index.mdx`
- ファイルパスが渡された場合: そのファイル
- 何も渡されなかった場合: `git status` と `git diff` で変更中の `.mdx` を探す

対象ファイルを全文読み、[`references/technical-checklist.md`](references/technical-checklist.md) を読んで次を特定する。

- 中心的な主張と結論
- バージョンや時期に依存する記述
- 仕様や API に関する規範的な主張
- 実行を意図したコード
- 検証環境と観測結果
- セキュリティ、互換性、運用上の影響

技術的な主張を含まない記事の場合は、その旨を報告して終わる。

## Step 2: 並列レビューの実行

3 観点について、それぞれ専門の subagent を**並列で**起動する。

| 観点 | Agent指示ファイル | 目的 |
|---|---|---|
| 一次情報の裏取り | `agents/evidence.md` | 主張が一次情報で裏付けられているか。バージョン依存の記述は現在も正しいか |
| コードと再現性 | `agents/code.md` | コードが動くか。手順を追って同じ結果になるか |
| リスクと互換性 | `agents/risk.md` | セキュリティ、秘密情報の漏洩、互換性、運用上の落とし穴 |

subagent 起動時に含めること:

- 対象ファイルの絶対パス
- 記事の全文
- 該当する agent 指示ファイルのパスと、それを読んでから作業する指示
- `references/technical-checklist.md` のパス
- プロジェクトルート (`/Users/p1ass/ghq/github.com/p1ass/blog`)
- 後述の「指摘してはいけないもの」

subagent 起動のプロンプト例:

```
技術記事を「{観点名}」の観点からレビューしてください。

まず .claude/skills/tech-review/agents/{観点}.md を読み、レビュー指示に従ってください。
あわせて .claude/skills/tech-review/references/technical-checklist.md も読んでください。

## レビュー対象
- ファイル: {絶対パス}
- プロジェクトルート: {ルートパス}

## 記事本文
{全文}

検索結果の要約だけで判断せず、必ず一次情報のリンク先を読んでください。
確信度の高い指摘のみ報告してください。根拠を書けた指摘だけを報告してください。
```

## Step 3: 結果のマージと出力

すべての subagent の結果を収集する。

1. 重複を排除する。同じ原因の指摘は統合する
2. 重要度順に並べ替える。`must` → `should` → `nits` → `question` の順とし、同じ重要度では行番号順にする
3. 未完了の検証を明示する。実行できなかったコマンドと確認できなかった主張を最後に列挙する

### ラベル

| ラベル | 用途 |
|---|---|
| **must** | 危険、または根本的に誤っている。公開を止める。動かないコード、事実誤認、秘密情報の露出 |
| **should** | 公開前に直すべき実質的な技術的誤り。根拠の不足、バージョンの記述漏れ |
| **nits** | 正確性を改善するが、なくても記事は成立する |
| **question** | 記事だけでは判断できず、筆者の意図や検証環境の確認が必要 |

### 出力フォーマット

各指摘は必ず 4 行構造で書く。**根拠を書けた指摘だけを報告する。**

```markdown
## Tech Review

対象: app/routes/posts/<slug>/index.mdx
レビュー観点: 一次情報の裏取り / コードと再現性 / リスクと互換性
検証日: YYYY-MM-DD

### 指摘事項

#### [must] コード行の指定に `gh pr review` を使っている
- 観点: 一次情報の裏取り
- 箇所: `app/routes/posts/example/index.mdx:58`
- 影響: 読者がこのコマンドを実行しても失敗する。記事の中心的な手順
- 根拠: `gh pr review --help` の出力と GitHub CLI のドキュメント (https://cli.github.com/manual/gh_pr_review) を確認したところ、行指定のオプションは `gh api` 側にのみ存在する
- 改善案: `gh api` を使う手順に置き換える。記事の後半で実際に使っているコマンドと揃える

#### [should] 対象の Go バージョンを明記する必要がある
- 観点: コードと再現性
- 箇所: `app/routes/posts/example/index.mdx:30-45`
- 影響: `for range` のループ変数の挙動は Go 1.22 で変わったため、読者の環境で結果が異なる
- 根拠: Go 1.22 リリースノート (https://go.dev/doc/go1.22) の "for loops" の項。記事のコードは 1.21 以前の挙動を前提にしている
- 改善案: 冒頭に対象バージョンを明記し、1.22 以降での挙動にも触れる

### 完了できなかった検証

- <実行できなかったコマンドと、その理由>
- <確認できなかった主張と、必要な情報>
```

指摘がない場合はその旨を書く。**出力は指摘事項のみとする。** 文章表現の問題は `article-review` に任せる。

## 指摘の対象外

- `{/* <!--more--> */}`: 記事一覧の要約を切るマーカー
- `<ExLinkCard url="..." />` `<Twitter url="..."/>` `<BlockLink href="...">` `<Note>`: このブログの MDX コンポーネント
- 画像直下の `_キャプション_`
- `<Twitter>` の URL が `twitter.com` であること
- `<!-- TODO: ... -->` コメント: 執筆中の未確定箇所を示す意図的なマーカー
- 文章表現や構成の問題: `article-review` の担当

## 修正の適用

ユーザーが修正を依頼した場合だけ、根拠で確立できる客観的な訂正を適用する。

- 論旨、範囲、筆者の意見を変える修正は、適用する前に合意を取る
- 修正後は影響する検証を再実行し、変更ファイル、コマンド、結果、未解決事項を報告する
